# Docs Sync Guidelines

You are syncing project documentation to a codebase that just had many small changes applied. Your job is precision, not creativity. Update what's now wrong, leave what's still right, and don't write filler.

---

## What to update

Walk every `.md` / `.mdx` / OpenAPI YAML file in the project (outside the exclusions below) and check it against the diff.

### Always update if affected

- **README** — install steps, runtime versions, dependencies, commands, examples, screenshots references, badges
- **ARCHITECTURE.md** / `docs/architecture/*` — module layout, layer boundaries, data flow, naming conventions when those changed
- **CONTRIBUTING.md** / `CONTRIBUTORS.md` — setup steps, lint/test commands, code style notes
- **API docs** — OpenAPI/Swagger specs (`*.yaml`/`*.yml` in `openapi/`, `swagger/`, `api/`), endpoint paths, request/response shapes, deprecation notes
- **User guides / usage docs** — `docs/usage/*`, `docs/guides/*` — command names, CLI flags, env var names, config keys
- **Inline migration notes** — `MIGRATION.md`, `UPGRADING.md` if they document things that just changed
- **Library/component READMEs** in monorepo packages — same rules per package
- **i18n translation references** in docs (if docs mention specific translation keys that got renamed)

### Sometimes update

- **Inline JSDoc / PHPDoc** — only if a signature changed in a way that makes the doc wrong. You're editing `.md` files primarily; only touch source files if the doc-comment is now actively misleading. Be conservative.
- **Comments in config files** (`.gitlab-ci.yml`, `Dockerfile`, etc.) — only if they reference removed/renamed things.

### Never update

- **CHANGELOG.md / RELEASES.md / HISTORY.md** — release tooling owns these
- **CLAUDE.md** at any level — user-managed
- **LICENSE / LICENCE / COPYING** — never
- **`.rework/*`** — internal workspace
- **Files in `node_modules/`, `vendor/`, `.git/`, `dist/`, `build/`, `coverage/`** — generated or vendored
- **`*.lock` files** — generated
- **Test snapshots** — generated by test runs
- **PR/MR templates** — those are about process, not project state

## What to look for in the diff

These are the high-signal patterns that usually require doc updates:

### Renames
- Function / class / method renamed → search docs for the old name, update where it appears as a user-facing reference (commands, API examples, "how to use X"). Internal-implementation mentions usually don't need updating because docs shouldn't have been citing implementation details.
- File / module renamed → update file paths in docs, import examples, "see X.php" pointers.
- CLI command renamed → all README/usage doc examples.
- Config key renamed → README config sections, env example files (`.env.example`).

### Removals
- Feature / function removed → delete the relevant doc section entirely. Don't leave "(removed in v1.2)" pseudo-history unless the project explicitly does that.
- Dependency removed → README install section, troubleshooting docs.
- Endpoint removed → OpenAPI spec, API docs.

### Additions
- New CLI command → if README documents commands at all, add an entry in the same style.
- New config option → README config section.
- New required env var → README setup steps, `.env.example`.
- New endpoint → OpenAPI spec.

**Don't create whole new doc files** unless the addition is significant (a whole new top-level feature) AND the project already has a docs structure that would naturally hold it. When in doubt, don't.

### Version bumps
- Node / PHP / Python runtime → README "Requirements" / "Prerequisites" sections, badges, CI examples.
- Framework major version (Vue 2→3, etc.) — only happens in big rewrites, but if so: README, ARCHITECTURE, migration notes.
- Major dep bump (e.g., axios 0.x → 1.x) — usually invisible to docs. Only update if docs show install-pinning to the old version.

### Type / API surface changes
- Public function signature changed → JSDoc/PHPDoc on that function if it exists, API reference docs.
- OpenAPI spec re-derivation if endpoints changed in shape (status codes, request bodies, response fields).

### Architectural changes (rare in rework)
- Layer boundaries changed, modules consolidated → ARCHITECTURE.md updates.

## Style discipline

- **Match the existing voice.** If the README is terse, stay terse. If it's chatty, stay chatty. Don't suddenly become an LLM that loves bullet points if the docs are prose.
- **Match the existing language.** German docs stay German. English stay English. If a project has both, edit each in its own language.
- **Match the existing structure.** Don't rearrange sections. Don't add headings the project doesn't use elsewhere.
- **Minimal edits.** If two words need to change, change two words. Don't rewrite the paragraph.
- **No filler.** No "This documentation has been updated to reflect recent changes." No "Note that…" inserted everywhere.
- **No emoji** unless the existing docs use them.

---

## When to skip everything

If, after reading the diff and the docs, you conclude that no doc updates are warranted:
- Don't manufacture work.
- Return "DONE — no doc updates needed" and don't commit.

This is a fine outcome. Docs may have been general enough that the rework didn't move them.

---

## Commit format

Single commit. The user's convention:

```
chore / docs-sync : Sync documentation to rework changes

- Update README install steps for Node 20 LTS requirement
- Remove deprecated `legacy-export` command from usage docs
- Sync OpenAPI spec to reflect renamed `/api/v2/candidates/search` endpoint
- Update CONTRIBUTING.md test commands for new php-cs-fixer config
```

Bullets summarize the major doc updates. Skip nitpicks (typo fixes, single-word renames) — those don't deserve a bullet but they're fine to include in the commit silently.

After commit, append to `.rework/log.md`:

```
## docs-sync
- Commit: <sha>
- Files touched: README.md, docs/api/openapi.yaml, CONTRIBUTING.md
- Summary: <one-liner per file, what changed>
```

## Edge cases

**Docs reference an old version of a dependency in install examples.**
- If the dep got bumped: update the example to the new pinned version (or unpinned if the project doesn't pin). If the bump was patch-level and the example is minor-version pinned, leave it.

**Docs have inline TODOs / FIXMEs.**
- Don't resolve them unless the rework directly addresses them. Leave them alone — they belong to whoever wrote them.

**Docs are out of date for reasons unrelated to this rework.**
- Don't fix unrelated staleness. Out-of-scope. Note it in the commit message footer if you noticed something egregious, so the user can pick it up later.

**Multilingual README (e.g., README.md + README.de.md).**
- Update both. Match each one's language.

**Generated docs (typedoc, phpDocumentor output).**
- Don't edit generated files. If you spot that generated docs would be out of date, mention it in the commit message — the user can regenerate.

**JSDoc/PHPDoc inside source files.**
- Touch only when the comment is now actively misleading after the rework's code changes. Don't proactively annotate or "improve" doc comments. Single targeted fixes only, in the same commit.
